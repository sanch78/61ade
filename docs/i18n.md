# Localization

Localization is part of every application, even a single-language site without
a selector. Framework catalogs cover Hungarian, English and German labels,
validation, runtime errors and login-verification mail. Consumers supply their
business translations; business text stays out of the framework.

<a id="konfiguráció"></a>

## Configuration

Optional root application JSON:

```json
{
  "i18n": {
    "default": "hu",
    "languages": {"hu": "Magyar", "en": "English", "de": "Deutsch"},
    "selector": true,
    "flags": {"hu": "hu", "en": "gb", "de": "de"},
    "catalogues": {"hu": "locales/hu.json", "en": "locales/en.json", "de": "locales/de.json"}
  }
}
```

Paths resolve from the application JSON directory. Catalogs are flat stable
message-key → translation objects. Existing declaration source text may itself
be a key; translating labels does not change field/action/object identifiers:

```json
{"Szintetikus elemek": "Synthetic items", "Üzleti címke": "Business label"}
```

PHP consumers use `ApplicationDefinition(languages: new Blade\I18n\Settings(...))`;
`LanguageConfiguration::build($definition,$pathResolver)` reads declarations.
Without a section: hu/Magyar, selector hidden. For English without selector:
`default: en`, `languages: {en: English}`, `selector: false`.
Default must be supported. Codes may be hu/en/de or valid xx-YY; additional
languages need consumer translations of framework messages. A single-language
site always hides the selector.

<a id="nyelvválasztás-és-hatókör"></a>

## Language selection and scope

The native Toolbar selector precedes themes and remains visible on mobile.
In login/confirmation/password-change windows, language is the first form row
(FB-0046): aligned `Nyelv` label, non-text-editable native Combo with selected
PNG and flagged options. This replaces the separate above-form Toolbar.
Names remain in their own languages: Magyar / English / Deutsch.
Optional flags select actual 16×11 PNGs (`hu`, `gb`, `de`). Toolbar uses native
`icon`; names stay text. No OS-dependent emoji or image-incapable HTML select.
Without flags only names show. Country mapping is explicit site configuration.
See [flag assets](flag-assets.md). Selection uses a CSRF-protected framework POST;
unsupported languages/invalid tokens cannot change preference.

The cookie named `${sessionName}_language` is HttpOnly, SameSite=Lax, Secure
on HTTPS, scoped to the site cookie path, lasting one year. Login/logout
preserve it. It is a browser preference, not authorization/profile state.
Switching reloads while retaining URL hash; unsaved form values are not
transferred. Sort/view/layout preferences use stable IDs.

HTML lang, HTTP Content-Language, bootstrap and backend translator share locale.
Bearer APIs may use `X-BLADE-Locale` from supported languages; unknown values
fall back to site default. Direct CLI/API code calls
`Translator::configure($settings,$locale)`. A general outage before config/DB
loading may use Hungarian fallback; this proves neither login nor SMTP delivery.

## Account default language

With multiple site languages and built-in user admin, Default language is editable
in form/grid (site default or a supported language); see [account switches](admin.md#fiókkapcsolók).

- Successful password/code/OAuth login sets the language cookie from the account default; later selector changes remain possible.
- Login-verification mail uses the account language regardless of current login-window language.
- A language later removed from site configuration is ignored in favor of site default.

Single-language sites have neither selector nor account language field.
JSON enables this through `i18n` plus `admin`; PHP uses
`Accounts(languages: $settings)`. Verification: `admin.php`, `contracts.php`,
and managed `demo.spec.cjs` with an English account, mail and UI.

## Translation contract

PHP `Translator::text($key,$parameters)` and TypeScript `t(key,parameters)`
resolve messages. Preserve placeholder names such as `{count}`, `{name}`,
`{minutes}`; rendering applies normal HTML escaping. Order: selected-language
consumer/framework catalogs, default-language consumer/framework catalogs,
original key. Consumers may override framework text. Add labels only through
the common translator and update every affected catalog.

Translation applies to presentation: menus, actions, fields, columns, layout
headers, validation, static choices and mail. Record data, passwords, IDs,
defaults, SQL and database lookup labels do not change. Dynamic business choices
translate known labels with `Translator::text`. Number formatting follows locale.
The common adapter configures native Suite message/grid/form/combobox/window/
toolbar locales where exposed. Technical names Suite cannot localize may remain
English. UI language does not translate content or databases automatically.

## Verification

- `php8.4 tests/shell/i18n.php`: fallback, placeholders, validation, static choices, unchanged data, mail rendering and catalog parity.
- The preserved `i18n` browser project tests three languages, in-modal switching, server login errors, frontend validation, mobile and hidden selector. It requires localhost fixtures and must not launch here; [host coverage limits](development.md#existing-full-smoke-and-coverage-limits) apply.
- Consumers separately check business declarations/errors/mail. Rendering tests do not send actual e-mail.

Historical 2026-10-17 results (FB-0034): i18n Chromium 3/3, six shell cases
including repeated localized confirmation, consumer integration 4/4 and actual
development load/switching 3/3 passed. PHP checks rendered mail; actual SMTP
delivery was outside that acceptance.
